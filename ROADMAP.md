- [x] B-12 — Release gate on B1/B2: a pack run (B-07) can now report pass or fail against the owner's score threshold, so a model or prompt change can be gated on a lab run. The threshold value stays the owner's call — the mechanism never hardcodes or defaults one. `local_models.run_pack` and `summarize_pack` take an optional `threshold` (percent, 0–100); when given, the leaderboard summary carries that `threshold` and a boolean `passed` (the pack's score as a percent meets it), and when absent it carries neither — a run without a configured threshold is neither a pass nor a fail. `lab/ollama_eval.py`'s pack entry point and its `--threshold` flag thread the value through to the written `runs/local-models/<id>/result.json`. In `lab/serve_lab.py`, `POST /api/local-runs {set:"pack", …}` accepts an optional `threshold`, validated with the same numeric/range pattern as the existing settings (a new `clean_threshold`: non-numeric or out of 0–100 is rejected 400, blank/absent stays `None`, never defaulted) and passed to the subprocess only when set; `GET /api/local-runs` per-pack rows carry `threshold` and `passed` through the summary. The Models tab's "Task packs" board shows a pass/fail badge on rows that have a threshold. Verified by unit tests in `tests/test_model_lab.py`: `run_pack` reporting pass when the score meets the threshold, fail when it is below, and neither field when no threshold is given; `ollama_eval.run_pack` writing `threshold`+`passed` into its result file (and neither without one); `clean_threshold` accepting valid values/blanks and rejecting out-of-range and non-numeric input; and the HTTP route rejecting an invalid threshold (150, -5, non-numeric → 400) while accepting a valid one. The stated full-pass count in CONTRIBUTING.md/README is updated to `375 passed, 1 xfailed` (the earlier `307` had drifted as tests were added). `make check` is the owner's gate; the HTTP route test binds a port and is skipped in a no-port sandbox, never deleted.
- [x] B-06 — Invoice B2 pack: `packs/b2_invoices.json` is a B-04 task pack (`id` "b2", name "Invoices B2 — synthetic Swiss invoice texts") of 43 synthetic Swiss invoice texts in German, each a realistic `Rechnung`/`Faktura` with an invented merchant, an invoice date, a gross total in CHF, a current Swiss MWST rate (8.1% standard or 2.6% reduced) and the contained VAT amount. Every task's prompt asks the model to answer only with a JSON object carrying `date` (ISO JJJJ-MM-TT), `total`, `vat_rate` and `vat_amount`; every `expected` is that dict and every `check` is "json" (scored by `json_fields_match` in `lab/text_tasks.py`). One convention throughout, stated plainly in each text: `total` is the gross amount incl. MWST, so `vat_amount = round(total * rate / (100 + rate), 2)`. Formats vary (amounts as `1'234.50` / `1234.50`, CHF/Fr. prefixes; dates as `14.01.2026`, `21. März 2026`, `2026-04-09`) while expected values stay consistent with the text. Data is strictly synthetic — invented company names, no real companies, IBANs, addresses or customer data. Verified by unit tests in `tests/test_task_packs.py`: the pack loads via `load_pack`, task count is within 30–50, every check is "json", every expected is a dict with exactly the four fields, `vat_rate` is in {8.1, 2.6}, `vat_amount` matches `total` and rate within 0.01, and ids are unique; the stated full-pass count in CONTRIBUTING.md/README is updated to `298 passed`. `make check` is the owner's gate.

- [x] B-03 — Text-answer task kind: `lab/text_tasks.py` adds a non-code `TextTask` and three pure checks — `exact_match` (equal after whitespace is collapsed), `json_fields_match` (answer parses as a JSON object and the named fields equal the expected ones) and `numeric_match` (answer parses as a finite number within a tolerance); a malformed JSON or non-numeric answer scores wrong instead of raising. Text tasks never touch the sandbox path (no `validate_source`, no `exec`): `local_models.answer_text_task`/`check_text`/`build_text_prompt` ask a local model and score its plain text by rule. Verified by unit tests in `tests/test_model_lab.py` covering all three checks (including malformed JSON, non-numeric and infinite answers, an answer that is Python code compared as text, and an unknown check kind rejected) plus a stand-in-Ollama wiring test; `make check` is the owner's gate.

- [x] B-04 — Task-pack file format: `lab/task_packs.py` defines a JSON pack (`id`, `name`, and a list of `tasks`, each with `id`, `input`, `expected` and a `check` that is one of the three B-03 kinds — `exact`/`json`/`numeric`, the last carrying a `tolerance`). `load_pack`/`validate_pack` check a pack as it is read, mirroring the level-5 validation style (`lab/try_task.py` validate, `lab/ladder.py` load_custom): a malformed pack raises a `ValueError` naming the offending task id and field (missing field, unknown check, duplicate id, non-numeric expected, misplaced tolerance, empty/absent fields, invalid JSON), and a valid pack becomes a `TaskPack` of B-03 `TextTask` objects ready for `text_tasks.score`.
